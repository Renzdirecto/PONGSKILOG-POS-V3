# Customer Experience (Phase 19.6)

## A customer screen belongs to a POS station, never to an account
Pair, unpair, mode, Live Cart and the order confirmation resolve the screen by (selected Branch from `ActiveBranchContext`, SHA-256 of the `X-POS-Station` header) and authorize with `PosAccess`. Never key a pairing, a cart or a mode on the signed-in user, and never accept a Branch or screen id from the client. `(branch_id, station_hash)` is unique: pairing a new screen releases the previous one (a racing pairing retries once). The screen device is identified only by its HttpOnly cookie hash and may read only its own projection; its only writes are its own presentation (pairing code, reset, header MENU / CUSTOMER DISPLAY, "confirmation shown").

## Modes are one column; only the Menu closes after an order
`customer_screens.mode` ∈ ads | menu | customer_display; `CustomerScreenMode::toggled()` under the row lock is the only press transition (POS header and screen header press the same mode; other control switches, same control → ads). A screen-side change or reset dispatches `CustomerScreenStatusChanged` on `branch.{id}.pos` so every POS header refetches its own status. After an order confirmation `afterOrderSuccess()` turns Menu into Ads (never reopens Menu); Customer Display stays. Ads + a live cart shows the full order summary; Menu + a live cart keeps the split. Never add a second mode flag or store the confirmation in the database.

## The order confirmation is started by the commit request, and counts down only once shown
Pay Now / Pay Later (the only paths that create the Kitchen ticket, including loaded Customer QR orders) call `ShowOrderOnCustomerScreen::afterCommit()` after their transaction, using the same request's `X-POS-Station` and `X-Customer-Screen-Cart` (last cart send, the in-flight fence) headers — never a second POS request, never Take Out only. It is rescued: nothing can roll back the payment. Each order is announced once per screen (replays show nothing). The confirmation waits in cache (`TAKEOVER_PENDING_MS`) until the screen reports it is on screen (number, and for Take Out the QR image loaded, or the 4 s readiness fallback) via `takeover/{id}/shown`; only then does the Branch duration (`CustomerScreenSettings`, 3–15 s, default 5 s) run. It is its own view (`customer-screen-takeover.tsx`), never the Customer Display board, and never carries a customer name.

## The Live Cart is display-only, derived and ephemeral
The POS sends ids and quantities only; `CustomerScreenCart` derives names/prices from `BranchCatalog` (no ids, no free-text notes). `CustomerScreenLiveState` keeps it in the cache (15 min) with a per-page-instance sequence guard and the confirmation fence. It is never an Order, never moves stock and is never read by payment code.

## Queue position has one source
Use `KitchenBoard::queue()` (the Customer Display "Preparing" column: Kitchen/Preparing, open Store Session, `(committed_at, id)`): overall position (Dine In + Take Out), same-type position and a bounded row window that always contains the order with its true positions — one query whatever the queue length. The confirmation and the pickup page both use it; never count in React or re-derive a second queue formula. The Customer Display board's bottom "Dine In: X / Take Out: Y" is that same Preparing column, counted by `KitchenBoard::customerDisplay()` from the rows it already loads (`counts`), never a second query.

## Pickup tokens: hash lookup, one per committed Take Out order
Issued by the after-commit `IssuePickupToken` listener (rescued) and ensured again, idempotently, before the confirmation — never inside a payment transaction. Look up by SHA-256 only; the raw token is kept encrypted solely to re-render the QR. Tokens never go into logs, audit or broadcasts (use `channel_key`). The public projection (`PickupStatus`) is an allowlist: order number, Take Out, status, Take Out + overall queue positions, the snapshot order summary (`CustomerScreenCart::customerLine`: no notes, ids or cost), receipt availability, the Branch's safe customer links and notification availability. The pickup receipt reuses `CustomerQrProjection::publicReceipt()` / `DigitalReceiptCard` without name, table or notes, and ends with the token (12 h, 410).

## Buzz: explicit opt-in, row-locked limits, separate push path
A scan never subscribes; only the page's button stores a `pickup_push_subscriptions` row (one per token). `BuzzPickupCustomer` decides under the token row lock (idempotency key, 5-s cooldown → 429, max 5 → 422) and `SendPickupBuzz` re-validates at send time and deletes rejected endpoints. Customer pushes go only through `PickupPushGateway` and `/pickup-sw.js` (scope `/pickup/`, no caching); never send them through `PushNotifications`/`PushRecipients`/`/sw.js` and never let staff messages read the pickup table. Nothing in the Buzz path writes order, Kitchen or payment state.

## Sounds: the push is the phone Buzz; custom MP3s are foreground-only and optional
A locked or backgrounded phone gets only the push notification (OS/browser sound and vibration where allowed) — never try to put a custom sound in the push. `/pickup-sw.js` also posts `{type: 'pickup.buzz'}` to that order's open page, which vibrates and, only while visible, plays `public/audio/customer-screen-buzz.mp3` (advertised by `PickupStatus::buzz_sound_url` only when the file exists; the first tap unlocks audio; a refusal is silent). The customer screen's own confirmation cue (`public/audio/customer-screen-success.mp3`, optional) is separate. Never commit or fabricate either MP3.

## Customer-facing colors and the confirmation fit
Dine In is GREEN, Take Out is BLUE (`orderTypeTone()` in `lib/customer-screen.ts`) on the board numbers, queue rows and the confirmation, always with the DINE IN / TAKE OUT text; the customer's own row is solid with a white ring and "YOU". The confirmation never scrolls: the order block scales to its box and the queue shows only whole rows that fit (`queueGrid()` + `fitQueueRows()`, a presentation window over the server rows that always keeps the own row — never re-ranked).

## Public pages have their own realtime client and named rate limits
`/customer-screen` and `/pickup/{token}` get no staff shared props, manifest or staff PWA runtime (`isPublicCustomerSurface`), send `private, no-store` + `noindex`, and authorize channels through their own capability endpoints (`lib/public-echo.ts`). Events are id/time invalidations; clients refetch. Their routes use named `RateLimiter::for()` limiters: an un-named `throttle:X,Y` shares one counter per account/IP with every other un-named throttle in the app (a Phase 20 item), so a frequent call (like the Live Cart) would starve low limits such as Void or Close Store.
