# Operations

## One canonical Ingredient balance per Branch
Ingredient stock is one `branch_ingredient_stocks` row per Branch + Ingredient, shared by every Plan; Plans never own stock. Only `ApplyIngredientMovement` writes it, appending an `ingredient_movements` row in the same transaction (lock rows in Ingredient-id order, after Store Session → Order → Product inventory). Quantities are exact numeric(18,4) handled as `ExactQuantity` integer ten-thousandths — never floats, never a direct balance edit, never a second ledger. Catalog › Inventory and Operations read the same balance. Lock order is Branch → balances: Operations-only writers (wastage, count, opening stock, Confirm) call `lockBranch()` (FOR SHARE) before any balance because POS commits hold the Branch FOR UPDATE and every movement insert needs a foreign-key KEY SHARE on it; `lock()` inserts only missing balances; Ingredient definitions use FOR NO KEY UPDATE so they never block sales' foreign-key checks. The PostgreSQL harness caught the inverted order as a real deadlock.

## Ingredient usage follows the canonical order lifecycle
Pay Now and Pay Later consume through `ApplyOrderInventory` → `RecordOrderIngredientUsage::commit()` once; `EditCommittedOrder` appends only the delta and `VoidOrder` restores the current net once, both from the Order's immutable `order_recipe_snapshots` (never today's recipe, cost or Plan). Settlement, payment corrections/allocations, Kitchen, Store Close, reports and broadcasts never move Ingredients. A Product that tracks Product stock at a Branch never also consumes Ingredients there (recipe save, add-on effect save and `UpsertBranchProduct` guard it for that Branch only). Recipe mode is per Branch (`branch_products.no_recipe_needed` + `tracks_inventory`): MAIN may use a Recipe while QAVE sells the same Product directly from Product stock; another Branch's tracking never blocks a recipe. Snapshots read only the committing Branch's mode, Recipes, Plan and effects.

## Recipe model: one Size group, Product-specific Add-on effects, no Instruction usage
A Product has at most one active `size` Group (enforced in `SyncProductModifierGroups` and `UpdateModifierGroup`; legacy duplicates are a configuration error from `ProductSizes::conflicts()`, never a guessed size). Only that Group creates base recipe variants (no Size group = one Regular recipe). `semantic_role = null` is shown as "Add-on / Modifier" and may carry a Product + option Ingredient effect (`product_modifier_effects`, never shared across Products); Instructions never move stock. A sale needs base recipe × item qty + Σ effect × item qty × modifier qty. Orders snapshot each Add-on's effect on first commit (`order_recipe_snapshot_modifiers`, a row without lines = "no effect"), so edits/voids never use today's effects.

## Recipe capacity is server-only and enforced
`RecipeCapacity` is the single formula (servings = min floor(max(stock,0) / per-serving), missing balance = 0) used by `BranchCatalog` (per-Size availability), `OrderSnapshots` (whole-order pre-check for new orders and Customer QR submit) and the capacity endpoints (`pos.recipe-capacity` counts; `qr.recipe-capacity` booleans only). A Product is Recipe-limited only once it has a recipe (products with no recipe keep their old availability); a Size without a recipe on such a Product is "Recipe required" and unsellable. Sales and usage-increasing edits must not drive an Ingredient below zero: `RecordOrderIngredientUsage` checks the whole order's net delta under the locked balances (supersedes the earlier "negative stock allowed for sales"). Voids and decreases are always allowed. Committed Ingredient changes and recipe edits dispatch `CatalogRealtime::ingredientsChanged()` (invalidation only). React never recomputes capacity.

## Pamamalengke money stays in the canonical Store Purchase
Confirm Pamamalengke writes exactly one Store Session expense through `RecordStoreSessionExpense::persist()` under the existing OPEN Store Session rule, plus exact restocks and purchase metadata, idempotently. Operations › Purchases is a projection; never add a parallel expense path or stored total. Recommendations come only from `ReplenishmentAdvisor`; COGS uses movement cost snapshots and unknown costs are reported incomplete, never ₱0. Cash after purchases is never labelled profit; Store-wide expenses are never allocated to a Plan. Stock mutations need one concrete active Branch from `ActiveBranchContext` (All Branches is read-only).

## Operations access is `operations.manage`
Every `operations.*` route and `OperationsAccess` require `operations.manage` (active, business-wide or with an active Branch assignment), not `inventory.manage`. Catalog › Inventory still reads Ingredient balances but links to Operations › Ingredient Stock only when the viewer holds `operations.manage`.

## Operations setup belongs to one Branch (pass #2.1, supersedes "shared definitions")
Ingredients (unit, target, purchase unit, cost, rule), Plans, Recipes (unique Branch + Product + size), Add-on effects (unique Branch + Product + option), recipe mode and Plan links carry `branch_id`; every read and write filters by the selected Branch (`OperationsAccess::configurationBranch()` for setup, `mutableBranch()` for physical stock) and `ownedBy()` answers 404 for another Branch's record. Recipe/effect/Plan lines may only use Ingredients and assortment Products of the same Branch (PostgreSQL composite FKs `(branch_id, ingredient_id|operation_plan_id)` back this up for stock, movements, Plan links and the working list). All Branches has no setup: pages show the Branch picker (Purchases lists every Branch). Any Operations manager of a Branch configures it; a Branch role only its assigned Branch. Never read an Ingredient/Recipe/Plan without a Branch filter and never add a global fallback.

## Configuration writers take the Branch configuration lock
Assortment add/remove/copy, recipe mode, Recipes, effects, Plans, Ingredient setup and setup copies call `BranchConfiguration::lock()` (Branch FOR NO KEY UPDATE) first; it conflicts with POS/QR commits (FOR UPDATE) and edits/voids/Giveaways/stock writers (FOR SHARE) but not with FK KEY SHARE checks. So a sale is entirely before or after a removal or recipe edit (never a removed Product sold, never a mixed recipe snapshot). Copies lock source (FOR SHARE) and destination in Branch-id order (`lockCopy()`), so opposite-direction copies never deadlock (PostgreSQL harness `tests/verify-branch-operations-postgres.php`).

## Setup copy is configuration only, clone once
`CopyOperationsSetup` (Operations › Copy setup, and "Copy Operations setup" in the Product copy) clones Plans, Ingredients and recipe mode/Recipes/effects for Products the destination sells; it never copies stock, movements, purchases, sales, sessions or audit. Destination records are matched by `lineage_id` then name within the Branch; existing setup is kept unless `replace` (future sales only); a matched Ingredient in another locked unit is a reported conflict, never reused. Preview is the same code path as the copy (dry run). Afterwards Branches change independently.
